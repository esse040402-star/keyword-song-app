## 1. 주제·사용자·문제

- 앱 주제 한 문장: **내가 직접 입력한 키워드와 앱에 미리 들어 있는 키워드로, 내가 저장해 둔 곡을 찾는 앱 (가칭: 키워드 곡함)**
- 선택 이유·7주차 주제 유지 또는 변경 이유:
  - 7주차 주제는 '나중에 노트'(할 일 메모)였고, **변경**했습니다.
  - 변경 전에 음악 추천 앱을 구상했으나 교수님이 "기존의 음악 앱과 다른 점이 없다"고 말씀하셨습니다 (구두 피드백, 날짜: [직접 작성]).
  - 그래서 방향을 바꿨습니다. 앱에 미리 들어 있는 키워드(예: 새벽, 운동)와 내가 직접 입력하는 키워드를 곡에 붙여 두고, 그 키워드로 내 곡을 찾는 앱입니다.
  - 제가 노래를 들을 때 키워드로 곡을 찾고 싶었는데 불편했고, 키워드로 노래를 찾는 앱이 있으면 좋겠다고 판단했습니다. 외부 음악 API·서버 없이 이번 학기 안에 끝낼 수 있는 크기이기도 합니다.
- 첫 사용자와 사용 상황: 음악을 들으며 곡을 키워드(분위기·상황)로 찾고 싶은 본인(대학생).
- 현재 해결 방법과 불편: 키워드로 곡을 찾고 싶었지만 그런 방법이 없어서, 곡 목록을 **직접 내려 가며 일일이 찾아야** 했습니다.
- 앱 사용 후 얻을 도움: 곡을 저장할 때 키워드를 붙여 두면, 나중에 키워드 하나로 그 키워드가 붙은 내 곡만 바로 모아 볼 수 있다.
- 조사 근거와 상세 기록 위치: `week09/analysis.md` (유사 앱: 애플 뮤직, 유튜브 뮤직 — 직접 조사 전)

## 2. 범위와 화면

- 핵심 흐름: **[앱 열기] → [곡 제목 입력 + 키워드 선택(미리 있는 키워드) 또는 직접 입력 → 추가] → [키워드를 선택하거나 입력해서 해당 곡만 찾기]**

| 기능 | MoSCoW 분류 | 이유·선행 조건 |
| --- | --- | --- |
| 곡 추가 (제목 + 키워드 1개 이상) | Must | 핵심 행동. 찾을 곡이 있어야 함 |
| 미리 있는 키워드 목록에서 선택 | Must | 직접 입력 부담을 줄이고 이 앱의 차별점. 앱에 목록을 상수로 포함하므로 선행 조건 없음 |
| 직접 입력한 키워드 사용 | Must | "내가 정한 키워드"가 핵심. 곡 추가에 포함 |
| 키워드로 곡 찾기 (선택 또는 직접 입력) | Must | 앱의 핵심 가치. 곡 추가 선행 |
| 앱을 다시 열어도 기록 유지 | Must | 나중에 찾으려고 저장하는 앱. 곡 추가 선행 |
| 빈 입력 검사·빈 상태·검색 결과 없음 안내 | Must | 입력 검증과 상태 안내는 핵심 가치 보호 (YAGNI로 삭제하지 않음) |
| 곡 삭제 | Should | 잘못 넣은 곡 정리. 없어도 핵심 흐름은 동작 |
| 아티스트 입력 | Should | 같은 제목 구분용. 없어도 동작 |
| 내가 추가한 키워드도 선택 목록에 표시 | Could | 한 번 쓴 키워드를 다시 입력하지 않게 함. 핵심 흐름이 먼저 |
| 곡 수정 | Could | 삭제 후 재입력으로 대체 가능 |
| 음악 재생·외부 음악 API·미리 곡이 들어 있는 곡 데이터·AI 키워드 제안·로그인·서버 동기화·알림·공유 | Won't this time | 계정·서버·유료 API·데이터 출처 확인이 필요. 다음 학기 후보 |

Must끼리의 의존: 곡 추가(제목 + 키워드) → 기기 저장 → 키워드로 찾기. 미리 있는 키워드 목록은 곡 추가·찾기 화면에서 함께 사용됩니다.

- **"미리 있는 키워드"의 의미**: 앱에 처음부터 들어 있는 **키워드(라벨) 목록**입니다. 곡 데이터가 아닙니다. 찾는 대상은 내가 저장한 곡이며, 곡이 미리 들어 있는 앱은 이번 학기에 만들지 않습니다.
- 미리 있는 키워드 초안(본인이 확정): 새벽, 운동, 공부, 드라이브, 비 오는 날, 휴식 — [직접 확인·수정]
- 이번 학기 제외 기능: 음악 재생, 외부 음악 API 연동, 미리 곡이 들어 있는 곡 데이터, AI 키워드 추천, 로그인·서버 동기화, 알림, 친구와 공유
- 화면 스케치: 화면 1개로 충분 (여러 화면을 강제로 추가하지 않음)

```
┌──────────────────────────────────────┐
│ 키워드 곡함                          │
├──────────────────────────────────────┤
│ 곡 제목   [________________]         │
│ 미리 있는 키워드 (눌러서 선택)       │
│  (새벽) (운동) (공부) (드라이브) ... │
│ 직접 입력 [________________]         │  ← 쉼표로 여러 개 (예: 카페, 집중)
│                          [ 추가 ]    │
│ ※ 오류 안내 표시 영역                │
├──────────────────────────────────────┤
│ 키워드로 찾기                        │
│  (새벽) (운동) (공부) ...  또는      │
│  [________________] 🔍               │
├──────────────────────────────────────┤
│ 목록 (전체 또는 검색 결과)           │
│  · 예시곡 A   #새벽 #드라이브        │
│  · 예시곡 B   #운동                  │
│ 곡이 없으면: "곡을 추가해 보세요"    │
│ 결과가 없으면: "해당 키워드의 곡이 없어요" │
└──────────────────────────────────────┘
```

## 3. 데이터·기술·위험

| 데이터 필드 | 자료형·예시 | 규칙·저장 위치 |
| --- | --- | --- |
| id | int · 1 | 곡마다 다름 · 기기 저장 |
| title | String · '예시곡 A' | trim() 후 비어 있으면 거절 · 기기 저장 |
| keywords | List\<String\> · ['새벽', '드라이브'] | 선택한 키워드 + 직접 입력(쉼표 분리 → trim → 빈 값 제거) 합쳐서 중복 제거 → 1개 이상 필수 · 기기 저장 |
| createdAt | DateTime · 2026-11-08 14:10 | 추가한 시각, 목록 정렬용 · 기기 저장 |
| artist (Should) | String? · '가수명' | 없어도 됨 · 기기 저장 |
| 미리 있는 키워드 목록 | List\<String\> (앱 상수) | 저장하지 않고 코드에 포함. 곡에는 선택한 키워드 문자열만 저장 |

- 찾기 규칙(첫 버전): 선택하거나 입력한 키워드와 **일치**하는 키워드가 붙은 곡만 표시. 미리 있는 키워드와 직접 입력한 키워드를 같은 방식으로 비교. 앞뒤 공백·영문 대소문자는 무시. 부분 일치는 **미정**.
- 재시작 뒤 유지할 데이터와 방법: 곡 목록 전체를 기기(브라우저) 로컬 저장소에 저장. 후보: `shared_preferences` (7주차에 후보로만 언급, **사용 가능 여부 미확인**).
- 실행 환경·배운 기술·새로 확인할 기술: Flutter 웹(Chrome) 계획 / 배운 것: 위젯, StatefulWidget, 리스트 / 새로 확인: 로컬 저장 패키지, JSON 변환, 선택 칩 위젯
- 외부 서비스·권한·비용·개인정보 범위: 없음. 계정·서버·유료 API 사용 안 함.
- 기술적 위험·미확인·대안:
  - 로컬 저장 패키지가 웹에서 동작하는지 미확인 → 안 되면 메모리 목록으로 먼저 완성하고 저장은 따로 확인
  - 저장 데이터 읽기 실패 시 안내와 빈 목록으로 시작하는 처리 필요
  - 키워드 직접 입력(쉼표 구분)이 불편할 수 있음 → 미리 있는 키워드 선택으로 부담을 줄임
  - 기존 앱(애플 뮤직, 유튜브 뮤직)에 비슷한 기능이 있는지 직접 조사 전 → 차별점은 가설
  - 곡이 처음에는 0개라 앱을 열어도 찾을 곡이 없음 → 첫 사용 때 직접 곡을 넣어야 함 (한계로 인정)

## 4. 앱 인수 조건

| ID | 시작 상태·행동 | 기대 결과 | 확인 방법 | 실제 상태 |
| --- | --- | --- | --- | --- |
| AC1 | 곡 0개 → 제목 '예시곡 A', 미리 있는 키워드 '새벽' 선택, 직접 입력 '드라이브' 후 추가 | 목록에 1개 표시(키워드 2개), 입력·선택 상태 초기화 | 목록·항목 수·입력란 확인 | 미실행 |
| AC2 | 곡 2개 → 제목 공백만 입력 후 추가 | 안내 표시, 곡 수 2개 유지 | 안내와 곡 수 함께 확인 | 미실행 |
| AC3 | 곡 2개 → 키워드를 선택도 입력도 하지 않고 추가 | "키워드를 1개 이상 선택하거나 입력하세요" 안내, 곡 수 유지 | 안내와 곡 수 확인 | 미실행 |
| AC4 | 예시곡 A(#새벽 #드라이브), 예시곡 B(#운동) 저장됨 → 찾기에 직접 입력 '드라이브' | 예시곡 A만 표시 | 결과 목록 비교 | 미실행 |
| AC5 | 같은 상태 → 찾기에서 미리 있는 키워드 '운동' 선택 | 예시곡 B만 표시 | 결과 목록 비교 | 미실행 |
| AC6 | 곡 0개로 앱 열기 | "곡을 추가해 보세요" 안내 | 첫 화면 확인 | 미실행 |
| AC7 | 곡 2개 저장됨 → 찾기에 없는 키워드 '없음' 입력 | "해당 키워드의 곡이 없어요" 안내 | 안내 확인 | 미실행 |
| AC8 | 곡 1개 추가 → 새로고침 | 같은 곡과 키워드가 다시 표시 | 새로고침 전후 비교 | 미실행 |

외부 요청이 핵심 기능이 아니므로 실패·재시도 AC는 저장소 읽기 실패 한 가지만 구현 단계에서 추가 검토합니다. 앱을 실행하기 전에는 통과로 바꾸지 않습니다.

## 5. 확인 결과와 첫 작업

- 교수님 확인 결과·확인 시점: **이 주제안은 미확인.** 이전 음악 추천 앱 구상에 대해 "기존의 음악 앱과 다른 점이 없다"는 구두 지적을 받았고, 이를 반영해 "직접 입력 키워드 + 미리 있는 키워드로 내 곡 찾기"로 수정했습니다. 수정안에 대한 확인은 아직 받지 않았습니다.
- 수정할 내용·담당·재확인 시점: 교수님 확인을 받은 뒤 기록. 확인 전에는 "다음 수업 시간에 확인받기" (담당: 본인) [직접 작성 — 날짜]
- 10주차 첫 화면·사용자 행동: 첫 화면에서 곡 제목을 입력하고, 미리 있는 키워드를 선택하거나 직접 입력한 뒤 '추가'를 누르면 아래 목록에 곡이 나타난다. (저장 기능은 그다음 작업)
- 관련 AC와 확인 방법: AC1, AC2, AC3 / `flutter run -d chrome`으로 실행해 입력 → 추가 → 목록 확인, 이어서 `flutter analyze`
