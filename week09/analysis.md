검토 방식·실제 사용한 도구: AI 사용 (Claude Code로 초안 작성). 짝 검토·교수님 확인은 아직 하지 않음.

> `[직접 작성]` 표시는 본인이 직접 조사하거나 교수님께 확인받아야 하는 부분입니다. 제출 전에 채우거나 "미확인"으로 남깁니다.

변경 전 구상: 음악 추천 앱 → 교수님이 "기존의 음악 앱과 다른 점이 없다"고 말씀하심(구두, 날짜 [직접 작성]) → 추천 기능은 외부 API·AI·서버가 필요해 제약과도 맞지 않아 폐기. **"직접 입력한 키워드 + 앱에 미리 있는 키워드로 내 곡을 찾는 앱"으로 수정.**

## 2. JTBD와 근거 구분

- **상황·하려는 일·현재 방법·불편·기대 효과**
  - 상황: 노래를 들을 때, 특정 키워드(분위기·상황)에 맞는 곡을 찾고 싶을 때
  - 하려는 일: 키워드로 곡을 바로 찾는다
  - 현재 방법: 곡 목록을 직접 내려 가며 일일이 찾는다
  - 불편: 키워드로 찾는 방법이 없어서 하나하나 확인해야 한다
  - 기대 효과: 키워드를 선택하거나 입력하면 그 키워드가 붙은 곡만 바로 본다
- **확인된 사실과 위치**: 아직 없음. 유사 앱 조사 후 3장에 기록.
- **개인 경험**: 노래를 들을 때 키워드로 곡을 찾고 싶었는데, 일일이 목록을 내려 가며 찾아야 해서 불편했다. (본인 경험, 본인 설명 기준) — 어떤 앱에서였는지는 [직접 작성]
- **가정과 직접 확인할 질문**
  - 가정 1: 애플 뮤직·유튜브 뮤직에서는 내가 정한 키워드로 내 곡을 찾을 수 없거나 불편하다 → 질문: 두 앱에서 곡에 키워드(태그·메모)를 붙이거나 그 기준으로 찾을 수 있는가?
  - 가정 2: 미리 있는 키워드가 있으면 직접 입력하는 수고가 줄어든다 → 구현 후 직접 써 보며 확인
  - 가정 3: 쉼표로 구분하는 직접 입력이 불편하지 않다 → 구현 후 확인
- **중간 확인 1의 지적·수정 결과·확인 시점**
  - 지적: 음악 추천 앱 구상에 대해 "기존의 음악 앱과 다른 점이 없다" (교수님, 구두, 날짜 [직접 작성])
  - 수정: 내가 직접 입력한 키워드와 앱에 미리 있는 키워드로 내 곡을 찾는 앱으로 방향 수정
  - 수정안에 대한 교수님 확인: **미확인**

## 5. 위험과 중간 확인 2

- **개발 시간·기술·저장·외부 의존·비용 점검**
  - 시간: 학생 1명, 10주차부터 구현. 화면 1개 + 목록 + 저장으로 범위가 작음
  - 기술: 위젯, StatefulWidget, 리스트는 배움 / 로컬 저장 패키지, JSON 변환, 선택 칩 위젯은 **새로 확인 필요**
  - 저장: 기기 로컬 저장. 웹에서의 동작은 **미확인**
  - 외부 의존·비용: 없음 / 개인정보: 곡 제목과 키워드만, 외부 전송 없음
- **줄일 기능과 유지할 핵심 가치**: 줄일 것 = 수정, 자동완성, 내 키워드 목록 표시. 유지할 것 = 입력 검증, 빈 상태·결과 없음 안내, 재시작 후 유지
- **한계**: 곡이 처음에는 0개라 사용자가 직접 곡을 넣어야 함. 곡을 미리 제공하지 않음.

## 6. 제출 전 대조

- 최종 요약과 분석 기록의 사용자·문제·필수·제외 기능 일치: 사용자=본인(대학생), 문제=키워드로 곡을 찾고 싶은데 일일이 내려 가며 찾아야 함, 필수=곡 추가·미리 있는 키워드·직접 입력 키워드·찾기·저장·검증과 상태 안내, 제외=재생·외부 API·미리 곡 데이터·AI·로그인·서버·알림·공유 → topic.md와 일치 (2026-11-08 AI 대조)
